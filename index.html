Overview系统概览

「为你推荐」信息流结合了两个来源的内容，并通过机器学习模型进行统一排序。

⚡

站内网络（In-Network）

来自你已关注账号的最新帖子，由 Thunder 模块在内存中实时维护，查询延迟在毫秒级以内。

🌐

站外网络（Out-of-Network）

通过 Phoenix 检索 从全量语料库中挖掘你可能感兴趣但尚未关注的账号内容，基于相似度搜索实现。

🤖

Grok Transformer 排序

两路候选合并后，由基于 Grok 的 Transformer 模型预测每个帖子引发各类互动的概率，生成最终排序分数。

🎯

零手工特征工程

系统彻底去除了人工设计的特征和大部分启发式规则。Transformer 直接从你的互动历史序列中学习内容相关性。

Components核心组件详解

系统由四个主要模块组成，各司其职、相互协作。

🎛
Home Mixer · 编排层
home-mixer/ · Rust
gRPC 服务

Home Mixer 是整个系统的调度大脑。用户每次刷新信息流，都会触发一次对 ScoredPostsService gRPC 接口的调用，Home Mixer 随即启动完整的流水线并最终返回排序好的帖子列表。

内部执行逻辑

①
接收请求：解析用户 ID，初始化流水线上下文（PipelineContext）
②
Query Hydration：并行拉取用户的互动历史序列（Action Sequence）和元特征（关注列表、设备、语言等），注入上下文
③
并行召回：同时向 Thunder（站内）和 Phoenix 检索（站外）发起请求，合并结果到候选池
④
候选 Hydration：并行补全候选帖子的核心数据、作者信息、媒体实体，候选携带完整特征才能参与排序
⑤
前置过滤：顺序执行 10 个过滤器，剔除明显不合格候选（去重/屏蔽/过期等），减少后续 ML 推断量
⑥
ML 评分链：依次调用 Phoenix Scorer → Weighted Scorer → Author Diversity Scorer → OON Scorer，得到最终分数
⑦
择优 + 后置过滤：取 Top-K，再做可见性兜底（删帖/违规），异步触发 Side Effects 写缓存

Thunder · 站内实时内容引擎
thunder/ · Rust
内存存储 Kafka

Thunder 解决的核心问题：如何在亚毫秒级内找到「你关注的人最近发了什么」？传统方案是实时查数据库，但对百万并发请求而言延迟太高。Thunder 的解法是把近期帖子全部常驻内存，用 Kafka 保持实时同步。

查询时：HomeMixer 传入用户的关注列表 → Thunder 批量取各关注账号的帖子 → 合并返回候选池

每个用户在 PostStore 中维护三条独立的帖子队列，按类型分开存储便于快速过滤：

📝 原创帖子
original_posts：用户直接发布的原始 Post，权重最高，优先纳入候选
💬 回复与转发
replies：含 @ 回复和 Repost，社交互动信号，可单独控制召回比例
▶️ 视频帖子
video_posts：单独维护便于视频流场景按需拉取，可精确控制视频内容占比
TTL 自动清理：每条队列都有保留时间窗口（Retention Period），超期帖子在写入新帖时顺带清除，无需独立 GC 线程，保持内存占用可控。
🔮
Phoenix · ML 推荐引擎
phoenix/ · Python (JAX)
Two-Tower Transformer

Phoenix 是系统的 ML 核心，分两个阶段处理推荐问题：先从海量帖子中快速筛出相关候选（召回），再对候选做精细评分排序（排序）。两个阶段共用同一套 Transformer 基础架构。

阶段一：召回 · Two-Tower 双塔模型

核心思路：把用户和帖子都映射到同一个向量空间，"越相似的内容，在向量空间距离越近"，用向量相似度代替逐条计算相关性，从而在百万帖子中快速找到最相关的候选。

用户塔（User Tower）
输入：用户特征 + 近期互动历史
经过：Transformer 编码
输出：用户 Embedding 向量 [D]
候选塔（Candidate Tower）
输入：帖子特征（文本/作者/媒体）
经过：轻量编码器
输出：帖子 Embedding 矩阵 [N×D]
相似度搜索：用户向量 · 帖子矩阵 = 相似度分数 → ANN 近似最近邻算法取 Top-K → 返回候选
离线预计算帖子 Embedding 并建索引，在线只需对用户向量做一次查找，效率极高

阶段二：排序 · Transformer + 候选隔离掩码

召回缩小到数百个候选后，用更强的 Transformer（移植自 Grok-1）做精细评分。关键设计是"候选隔离"：每个候选帖子的评分只取决于用户上下文，不受同批次其他候选影响。

输入序列 = [用户 Embedding] + [历史帖子序列 S 个] + [候选帖子 C 个]
Transformer 处理：带特殊注意力掩码的多头自注意力 + FFN，候选位置只能 attend 用户与历史，不能 attend 其他候选
输出：取候选位置的隐状态 → 线性投影 → [B, C, 15]（每个候选 × 15 种行为概率）
为何候选隔离重要？若候选能互相 attend，则同一帖子在不同批次中分数不同，无法缓存，也难以公平比较。隔离后每条帖子的分数只与用户相关，具有确定性。

Candidate Pipeline · 可复用流水线框架
candidate-pipeline/ · Rust
Framework

Candidate Pipeline 是整个系统的基础设施层，提供一套标准化的 Rust Trait（接口），让 HomeMixer 的业务逻辑可以专注在"做什么"，而不用操心"怎么调度、怎么并行、怎么容错"。类比理解：它就像 Web 框架之于业务接口——有了框架，你只需实现路由处理器，其余的由框架搞定。

六大核心 Trait 及其职责

📡
Source · 候选来源
定义"从哪里拿候选"。实现者：ThunderSource（内存查询）和 PhoenixSource（gRPC 调用 ML 服务）。框架会并行调用所有 Source，合并结果。
💉
Hydrator · 数据丰富
定义"给候选补全什么数据"。多个 Hydrator 可并行执行，例如同时拉取帖子正文和作者信息，而不是串行等待。每个 Hydrator 只修改自己负责的字段，互不干扰（不可变模式）。
🚫
Filter · 过滤
定义"哪些候选应该被丢弃"。每个 Filter 返回 true/false，框架收集所有 Filter 的结果后统一过滤，避免重复遍历候选列表。失败容错：单个 Filter 报错不会中断整条流水线。
📊
Scorer · 评分
定义"如何给候选打分"。多个 Scorer 顺序执行（后一个可基于前一个的分数），框架负责将每个 Scorer 的输出累加或覆盖到候选的分数字段上。
🏆
Selector · 择优
定义"如何从候选中选出最终结果"。默认实现是按分数降序排列后取 Top-K，也可扩展为带约束的选择（如强制保留一定比例的站外内容）。
📝
SideEffect · 副作用
定义"流水线完成后还需要做什么"。异步执行，不阻塞响应返回。典型用途：将本次服务的帖子 ID 写入"已服务缓存"，供下次 PreviouslyServedPostsFilter 使用，形成闭环。
设计收益：新增一个数据源只需实现 Source Trait；新增一条过滤规则只需实现 Filter Trait。框架负责调度、并行、日志、监控，业务代码零感知，测试也可以完全隔离。

Pipeline七阶段流水线

每个请求按顺序经历以下七个处理阶段，各阶段之间独立且可并行。

1

Query Hydration · 查询上下文增强

从数据存储中获取用户的近期互动历史序列（点赞、转发、回复等）以及关注列表、用户偏好等元信息，为后续召回和排序提供上下文。

互动历史 关注列表 用户特征
2

Candidate Sourcing · 候选召回

并行从两个来源拉取候选帖子：
Thunder 返回已关注账号的最新帖子（站内，亚毫秒级）
Phoenix 检索 通过 Two-Tower 相似度搜索返回站外推荐帖子

Thunder 站内 Phoenix 站外 并行执行
3

Candidate Hydration · 候选数据丰富

为每个候选帖子补全额外数据，确保排序模型有足够的输入特征。

核心帖子数据（文字/媒体） 作者信息 视频时长 订阅状态
4

Pre-Scoring Filters · 评分前过滤

移除不应参与评分的候选，减少计算浪费，并保证内容质量。

重复帖子 过期内容 自己的帖子 已屏蔽作者 静音关键词 已看过的帖子 付费墙内容
5

Scoring · ML 多维评分

依次应用四个评分器，最终分数综合了模型预测、多样性保障和站内外平衡：

Phoenix Scorer — Grok Transformer 预测各类互动概率
Weighted Scorer — 加权合并多个预测概率为单一分数
Author Diversity Scorer — 对同一作者反复出现进行分数衰减
OON Scorer — 对站外内容进行分数调整
6

Selection · 候选择优

按最终分数降序排列所有候选帖子，选取分数最高的 Top-K 个候选，准备进入最终过滤阶段。

降序排列 取 Top-K
7

Post-Selection Processing · 后置处理

对已选出的候选做最终校验：过滤已删帖、垃圾内容、暴力内容等；对同一对话的多个分支进行去重。

VF 可见性过滤 对话去重

Scoring评分与排名机制

理解 X 如何计算"你有多大可能与这条帖子互动"。

最终分数 = Σ (权重ᵢ × P(行为ᵢ))
正向行为（点赞、转发、分享）权重为正 · 负向行为（举报、拉黑、静音）权重为负

Phoenix Transformer 同时预测 15 种互动概率：

👍 点赞 Favorite
💬 回复 Reply
🔁 转发 Repost
💬 引用 Quote
🖱 点击 Click
👤 访问主页
▶️ 视频播放
🖼 展开图片
📤 分享 Share
⏱ 停留 Dwell
➕ 关注作者
👎 不感兴趣
🚫 拉黑作者
🔇 静音作者
⚠️ 举报 Report

💡 直观理解

如果模型预测你有 80% 可能点赞这条帖子，10% 可能拉黑作者，那么这条帖子的原始分数就是：

分数 = 0.80 × 正权重(点赞) + ... + 0.10 × 负权重(拉黑)

权重由工程师根据业务目标手动设定，但特征全部由模型自动学习——这是系统消除手工特征工程的核心所在。

Filtering过滤机制详解

过滤分两轮进行：评分前去除明显不合格候选，评分后做安全兜底。

评分前过滤（Pre-Scoring）

过滤器目的
DropDuplicatesFilter去除重复帖子 ID
CoreDataHydrationFilter移除核心数据缺失的帖子
AgeFilter过滤超出时间窗口的旧帖
SelfpostFilter不推荐用户自己发的帖子
RepostDeduplicationFilter去除同一内容的重复转发
IneligibleSubscriptionFilter过滤用户无权限访问的付费内容
PreviouslySeenPostsFilter过滤用户已经看过的帖子
PreviouslyServedPostsFilter过滤本次会话中已下发的帖子
MutedKeywordFilter过滤含用户静音词的帖子
AuthorSocialgraphFilter过滤被屏蔽/静音作者的帖子

评分后过滤（Post-Selection）

过滤器目的
VFFilter可见性过滤：删帖、垃圾、暴力、血腥等
DedupConversationFilter同一对话的多个分支去重

为什么分两轮？

前置过滤在 ML 推断之前运行，减少昂贵的 Transformer 推断开销。

后置过滤是最终安全兜底，确保即使在排序后仍能过滤违规内容（如帖子在排序后被删除）。

Design关键设计决策

这些设计选择使系统既简洁又强大。

1零手工特征工程

系统完全依赖 Grok Transformer 从用户互动历史序列中自动学习内容相关性，无任何人工设计的内容相关特征。这大幅降低了数据管道和服务基础设施的复杂度，让模型能自适应用户行为变化。

2候选隔离排序（Candidate Isolation）

Transformer 推断时，候选帖子之间无法相互注意——每个候选只能独立关注用户上下文。这保证了一条帖子的分数不受同批次其他帖子影响，分数结果稳定且可被缓存复用。

3基于哈希的 Embedding 查找

召回和排序模型均使用多个哈希函数进行 Embedding 查找，而非维护显式 ID→向量映射表。这避免了巨大的词表存储开销，并天然支持未见过的新用户/新帖子（无需 OOV 处理）。

4多行为同时预测

模型不只预测单一"相关度"分数，而是同时输出 15 种互动行为的概率。这使得最终打分公式可以灵活调整各行为权重（如提升转发权重、降低仅点击权重），无需重新训练模型。

5可组合流水线架构

candidate-pipeline 框架将流水线执行监控与业务逻辑完全解耦。各阶段可独立测试、替换、并行运行，新增数据源、过滤器、评分器只需实现对应 Trait，不影响其他阶段。
